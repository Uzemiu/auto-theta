- `play-record.py` 的观测操作始终请求 `include_map=True`，使关卡 `events` 中反复保存完整地图；世界探索日志同样包含多次完整观测。这比配置文件数量更值得改进。
- 本次顶层 79 份 JSON 解析后去除排版空白，序列化为紧凑 UTF-8 JSON 约 14.84 MiB（15,563,138 字节），较磁盘文件少约 66.3%。这是等价紧凑序列化的估算，说明排版也占较大比例；本次未改写文件。
- 最大两份为 chapter1-world.json（约 7.76 MiB、68 个事件）和 chapter2-world.json（约 6.23 MiB、22 个事件），其次为 2-11.json（约 3.44 MiB、35 个事件）。体积优先优化世界地图和关卡过程观测，不能仅删除几个小配置就解决。

- 先减少重复观测，再考虑紧凑格式。直接压缩为归档会影响现有脚本读取，需先适配消费者；当前没有紧急磁盘空间问题的证据。

## 后续记录规则

- 每关以一个 `<关卡号>.json` 为主，集中存放初始状态、动作回执、关键机制实验与完成状态。
- 在该关文件中分别保留完整初始地图及最终完成证据；中途只在新机制、预测失配、失败或关键检查点保留完整观测，不为每次普通移动重复写整张地图。
- 最终证据也可以是含正确关卡 ID 和 `completed=true` 的真实执行回执，不强求完整最终地图。用最后关内观测、已执行动作和存档状态/动作记录交叉核验；如 2-8 已自动离开关卡后，只保留实际捕获的完成回执并注明完整快照缺失，不因此重放整关，更不能拼造一次不存在的观测。
- 普通步骤保留输入、执行回执、关键动态状态即可。世界线分支、时间刻度或地图变化必须保留能复原差异的状态，不能把变化的地图误判为重复静态内容。
- 机制实验记录问题、动作、结果和结论；假设与已验证事实分开标注。
- 临时求解文件放入 `scratch/`，阶段交接后确认无依赖再清理。可复用配置保留在关卡记录或单独配置中。
- 合并旧文件时同步更新机制、解法、收集物和进度中的引用，并执行 `tools/audit-knowledge.py`。不要只按文件名包含 initial、evidence 或 current 就删除。
- 本次只完成必要性判断和规则更新，未删除、重写游戏证据，也未改变正在运行的记录脚本；后续清理应在控制 agent 的阶段交接点执行。

核心结论：需要保留可复现、可验收的证据，但不需要永久保留每个独立快照文件。主要问题是资料分散和重复观测，而不是当前磁盘占用。
